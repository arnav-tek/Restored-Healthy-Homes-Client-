## Walkthrough and boundaries

1. **Existing admin work:** use `/admin/login` → Quick access → Administrator. Application/credential decisions, profile edits, membership and featured scenarios, analytics, activity, Q&A, reviews and consultations remain available. Payment scenarios never override rejection or suspension.
2. **Categories:** open Categories, supply a unique display name, description and explicit whole-dollar preview price, then create. A generated immutable ID and separate synthetic billing mapping are assigned; neither depends on the label. Existing category IDs/prices/associations remain unchanged. New categories appear in applications/profile editors, Q&A and consultation selectors and matching, analytics and Certifications. Rename preserves identity, price and associations. The canonical server directory/pricing catalog remains the approved eight categories. New setup prices are session examples, not approved production billing; combined-category billing is still unresolved. The preview supports up to 32 categories and does not offer category deletion or reassignment.
3. **Certification editor:** select an existing or added category. Edit provider/program name, HTTPS source URL, program type, introduction, description, entry requirements, steps, timeline and external costs. Save as draft, review, then publish. Only published fields override Certifications in this tab. Saving an edited publication returns it to draft; original public reference copy remains until republished. Added categories without published copy show the honest pending-content fallback. This editor changes education references, never a member's verified-credential status. Final provider/program/content choices need client approval.
4. **Profile identity:** member and admin profile forms now have optional public professional/owner name and public email, separate from private application name/email. Blank public fields stay absent; no private fallback is used. Both fields are validated, allowlisted and clearable. They appear in member/admin public-field previews. For the explicitly associated Fern/Cedar/Hearthside examples, eligible in-tab identity updates also appear in a professional/owner identity block on the linked public profile; canonical sample business contact details remain separate. Arbitrary names/emails never establish account ownership. Existing phone/website fields remain explicitly public. Changing application contact information does not change the sign-in preset.
5. **Content:** save a resource draft, review it and publish. Resources now includes published session articles alongside original samples, with a working detail route. Drafts and unpublished articles are excluded from public selectors. Editing a publication returns it to draft. Text is rendered as escaped text, with no raw HTML. Generic no-index metadata and neutral HTTP 200 HTML are used for syntactically valid session resource IDs; missing/unpublished/reset records show an honest unavailable state after hydration. Unknown non-session slugs retain real 404s. Refresh cannot recover tab-only articles or identity edits.
6. **Responsive/accessibility polish:** category cards use native buttons; public identity, resource titles and paragraphs wrap long text; editors reuse the established sage/cream/clay typography and form patterns. The analytics table is a named keyboard-focusable scroll region. Keep client-approved copy/media and final legal/company material pending rather than inventing it.

## Structure for future accounts/data

`src/domain/session-catalog.ts` derives the current catalog without mutating canonical definitions. `src/domain/editorial.ts` owns certification types and the published-only allowlist. `src/validation/admin-editors.ts` validates category and education input; `src/validation/application.ts` owns opt-in public identity validation. Safe public reference seeds stay in `src/data/demo/`; original editorial resources remain server-backed sample adapters. Components compose the existing typed session commands and share accepted records/drafts.

The public certification island receives only public reference copy and category ID/name DTOs. Session resource and identity islands apply explicit projections to local records; no private server record is passed to them. No content draft is sent through HTTP requests. New category IDs in dashboard URLs select views only; mutations still require the selected admin scenario and an actual current category. This remains a fictional identity switch, not authentication or authorization.

Supabase integration still needs server-verified sessions/ownership/admin permissions, migrations, RLS/grants, account/profile separation, secure storage and adversarial testing. Real content publishing needs server permissions and published-only reads; real billing must replace scenario commands with verified events. Server timestamps and durable protected activity records must replace browser/session metadata. Client approval and launch/security/performance/device checks remain separate acceptance items.
