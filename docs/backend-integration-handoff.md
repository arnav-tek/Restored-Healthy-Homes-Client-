### Queue, routing and delivery rules

- An INSERT trigger creates one notification job in the **same transaction** as each new recipient-bound inquiry. A unique inquiry reference enforces one intended notification. Rejected, rate-limited, failed and duplicate/replayed submissions create no additional job. No existing inquiries are backfilled. Worker/provider failure cannot delete the saved inquiry. The public receipt contains only `saved: true`; the form says **“Your inquiry has been saved.”** Member inbox access remains independent.
- The trigger snapshots the accepted inquiry's original recipient and confirmed **Auth email**, never its sender address or editable public contact. Immediately before a provider call, routing checks the snapshot, current listing owner, protected member role, email confirmation, email equality and account availability. Email/owner/role changes, deletion or a ban cancel the notification without rerouting it. The original member retains B1 inbox history. Listing eligibility at submission is unchanged; later membership/suspension changes do not erase accepted inquiries.
- Server-only HTML/plain-text templates contain a generic notice and authenticated inbox link built from `RHH_AUTH_ORIGIN`. No sender name/address, project or message content enters the email. HTML links are escaped; addresses/origins are validated. No automatic email to the sender. Provider-approved From verification remains a future adapter requirement.
- Atomic `FOR UPDATE SKIP LOCKED` claims use 120-second leases and UUID fencing. A run starts at most three jobs, with a 15-second provider deadline, 10-second database request deadlines and a bounded run budget. Abandoned work is reclaimed; stale workers cannot prepare or finish a new lease. Safe temporary failures retry with exponential backoff/jitter and bounded Retry-After. Limits: five automatic attempts, at most two audited admin retries, seven lifetime attempts and 24-hour job age.
- Job states distinguish `accepted` (**provider acceptance only**), `test_recorded`, failed, canceled and `unknown`. There is no sent/delivered assertion. The injected test adapter records only `test_recorded`, with no acceptance timestamp or external side effect; it cannot be enabled through environment configuration. Timeout/lost responses are ambiguous. Retry after a possible send requires the same pinned provider/sender/origin/mode, stable idempotency key and a still-valid provider guarantee; otherwise the job is quarantined as unknown. Provider-contract limitations can still permit duplicate email: one job is not a promise of exactly-once delivery. Unknown jobs require operator/provider reconciliation, not blind retry. No webhooks or mailbox-delivery tracking are implemented.
- Three private forced-RLS tables hold jobs, sanitized attempt history and hashed worker keys. Neither ordinary users nor anonymous requests can inspect them. The NOLOGIN/NOBYPASSRLS worker cannot read inquiry bodies, reroute jobs, rewrite their age, or grant itself retries. Only the scoped worker header can invoke its exposed RPCs; member/admin sessions do not confer bulk-send authority. Private definer routines have fixed safe search paths and restricted execution.
- `/admin/notifications` reuses validated server identity/protected account roles. It exposes status, sanitized codes and attempt/retry history, **not** contacts, message bodies, provider receipts or keys. A reason and expected version are required for a known-failed retry; stale/conflicting retries return 409. Unknown outcomes cannot be retried there. API responses are private/no-store. No private delivery values or worker modules enter browser bundles.
