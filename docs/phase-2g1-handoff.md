# Phase 2G-1 handoff

Implemented 2026-10-04. Public demo reviews only; stop before 2G-2, real integrations, deployment or push.

## Behavior

Eligible professional profiles now include fictional published reviews, an average/count calculated from that same complete set, and a separate review form. Empty profiles show “No reviews yet” without a zero rating. Fern & Field demonstrates four published reviews, including pagination; Cedar Path demonstrates no reviews; the healthy-designers profile demonstrates longer text. Reviews are ordered by publication date descending, then stable ID ascending. `reviewPage` accepts a single positive integer (up to five digits), defaults invalid/duplicate values to 1 and clamps to available pages of three. Links remain on the current profile at `#reviews`, preserving the validated directory return. Directory sorting and filters are unchanged; no review structured data is emitted.

The provisional guest form asks only for a fictional display name (2–80 characters), integer rating (1–5) and written review (20–2,000 characters). Validation trims text within raw length limits, allowlists fields, shows an error summary and focuses the first invalid control. No contact information, service proof or medical information is requested. Native submission stays disabled before hydration and without JavaScript; published reviews and pagination remain readable/usable.

Drafts use `review:<professionalId>` in the existing provider, survive client navigation and never appear on another profile. Submission creates a pending record, clears its draft and locks that form attempt until “Start another demo review.” Confirmation states that nothing was published or delivered. Submitted records never enter public lists/totals. Sign-out/switching clears drafts with the existing discard confirmation while retaining submissions. Confirmed global reset/refresh clears the entire session. This is a local walkthrough, not verification, authorization or production duplicate/abuse prevention.

## Contract for 2G-2

- `ReviewRecord` is server-side seed data with immutable review/professional IDs, display name, integer rating, body, status, publication date and private moderation/contact fields. `review-fixtures.ts` is server-only and must never be imported by the client provider.
- `ReviewRepository.listPublic(professionalId)` reuses the directory adapter’s eligibility before projecting. Missing/ineligible targets return `null`; eligible empty targets return `[]`. `PublicReview` explicitly exposes only IDs, display name, rating, body and publication date. `publicReviewsFor` filters publication/target and orders results; `summarizeReviews` calculates count and a one-decimal average (`null` when empty).
- `DemoSession.publicProfessionalIds` is an ID-only snapshot from the existing eligible public directory, not a second catalog. Local member/admin listing edits still do not update that server directory. The form derives its target from the eligible server profile; the reducer rechecks this snapshot and ignores form-supplied target/status/verification data.
- `DemoSession.reviews` contains `submissions`, `currentByProfessional` and `nextSequence`. Session IDs are stable within the tab session (`demo-session-review-N`); reset starts a new lifetime. Submissions explicitly contain only ID, professional ID, display name, rating, body and forced `pending` status. No public overlay or admin/member review actions exist yet. Later moderation must maintain projections, profile eligibility and shared summary calculations.
- Public-directory professional IDs and member-workspace example IDs are distinct today. Phase 2G-2 must define explicit stable account-to-professional associations for any member ownership view; do not infer ownership from names, categories or submitted fields.

## Limitations and remaining decisions

No real persistence, network submission, email, cookies/browser storage, account creation or integrations. No verified-customer labels, member replies, editing, reporting, publication/rejection controls or removal actions. The client still needs to decide who may review, proof/service verification, duplicates/abuse controls, moderation, editing/removal and dispute rules before production implementation. Real services require server authentication/ownership where applicable, database policies and renewed security tests. All other approved backlog features remain in the checklist.
